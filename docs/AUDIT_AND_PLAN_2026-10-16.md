## 1. Короткий вывод

1. **Тема жизнеспособна, ядро есть.** Работающее офлайн Android-приложение: камера → нейросеть на телефоне → рамки и подписи → голосовое управление → журнал. Это уже больше, чем у типичного диплома на этапе октября.
2. **Исходное описание темы нельзя нести на защиту.** В прикреплённом DOCX стоят неподтверждённые числа (mAP 93,4 %, WER 6,8 %, 25–40 мс, «1280 очагов», «степень поражения 18 %») и технологии, которых в проекте нет (Whisper, Porcupine, TFLite/NCNN, Room, FastAPI, UVC, GoPro, ESP32). Реальные метрики в 2–3 раза скромнее. Исправленная версия уже лежит в `docs/thesis/2026-10-05/AgroVoice_Opisanie_Temy_i_Steka_2026-10-05.docx`, но прикреплён старый файл.
3. **Из 4 подсистем темы реализованы 2,5:** детекция есть, голос (команды) есть, TTS частично. **Базы знаний СЗР и сервера нет вообще.** Клиент-серверная часть, которая стоит в названии архитектуры, отсутствует.
4. **Главная проблема — процесс, а не код.** С 6 октября продукт не продвинулся: новая выборка в состоянии «0 принятых изображений, 0 GPU-запусков», а работа ушла в многоуровневые аудиты (55 992 записи в очереди проверки, валидатор preflight на 1 469 строк, SHA каждого файла). Репозиторий раздулся до 3,2 ГБ, последний коммит не отправлен на GitHub. При таком темпе к маю будет идеальный аудит данных и не будет диплома.
5. **Приложение сейчас — «лаборатория моделей», а не продукт для агронома.** 9 режимов моделей, пороги, сравнение — полезно разработчику, но не пользователю. APK весит 265 МБ.

### 2.2 ML-пайплайн (`ml-pipeline/`, ≈ 12 600 строк Python + 33 PowerShell)

- Очистка PlantDoc: точные дубликаты, EXIF, разделение групп по выборкам (`dataset_clean_v1/v2`).
- clean v2: 29 классов PlantDoc + «лист огурца, состояние неизвестно»; 2609 train / 349 val / 236 test.
- Обучение на AMD RX 9060 XT через WSL2 + ROCm, мягкая остановка и возобновление.
- Серии: 10× YOLO11n, 10× YOLO26n, 10× YOLO26s, 2,5× YOLO26m, пилоты классификаторов и DEIMv2.
- Экспорт в ONNX, сверка ONNX с PyTorch, упаковка с SHA, бенчмарки на телефоне.

|---|---:|---:|
| YOLO11n | 0,327 ± 0,004 | — |
| YOLO26n | 0,354 ± 0,008 | 0,488 (seed 12) |
| YOLO26s | 0,353 ± 0,007 | 0,481 (seed 04) |

## 4. Что работает криво

### 4.1 Android

1. **Мёртвый код с фейковыми данными.** `MainActivity.kt` не объявлена в манифесте. Она и `data/PhytoDbHelper.kt` нигде не используются. Внутри — «Топаз, КЭ (2.0 мл / 10 л)», «степень поражения 18,5 %» и `onUpgrade`, удаляющий все таблицы. Комиссия может открыть файл и найти это.
2. **Два способа хранения и ни одной нормальной БД.** Журнал — каталог JSON-файлов. При каждом сохранении `InspectionJournal.save` перечитывает и парсит все файлы. Нет схемы, миграций и связей «осмотр ↔ фото ↔ детекции ↔ участок».
3. **Бесконечный рост файлов результатов.** `FieldDemoViewModel.analyze()` пишет новый JSON в `results/` при каждом анализе: смена порога, модели, культуры, «сравнить модели» (9 файлов). В `init` последнее фото **автоматически анализируется при каждом запуске** — это ещё один файл и лишняя нагрузка. Очистки нет.
4. **Фото с камеры хранится дважды.** `PlantCamera` сохраняет в `DCIM/AgroVoice`, потом `importPhoto` копирует снимок в `files/photos`. Импортированные копии никогда не удаляются.
5. **Модели копируются по нескольку раз.** `FieldDetector.graph()` называет файл по id режима, а не по хешу ассета. Поэтому `yolo26n.onnx` (9,7 МБ) лежит в `files/models` пять раз: свой режим + 4 двухстадийных. Кроме того, все 212 МБ моделей и 88 МБ Vosk копируются из APK во внутреннюю память. Итог: установленное приложение занимает ≈ 2× от размера APK, то есть около 600 МБ.
6. **APK 265 МБ.** В продуктовую сборку зашиты 9 моделей: экспериментальные DETR, 4 классификатора и YOLO26m (1,4 с на Note 7). Агроному нужна одна.
7. **Интерфейс лаборатории, а не продукта.** На главном экране — чипы девяти моделей, слайдер порога, «Сравнить модели», «Полевые инструменты · тестовые». Нет экранов «Участки», «Справочник», «Отчёт».
8. **Архитектура UI.** Вся навигация — набор булевых флагов в одной Activity на 380 строк (`cameraOpen`, `galleryOpen`, `noteOpen`, `journalOpen`, `helpOpen`…). Код плотный: по нескольку операторов через `;` в строке, функции в одну строку на 300+ символов. Это тяжело поддерживать и показывать комиссии.
9. **Слайдер порога стирает результат при перетаскивании.** `changeThreshold` обнуляет `result` на каждом шаге, хотя анализ запускается только в `onValueChangeFinished`.
10. **Нет класса «не лист / не знаю».** Модель всегда отвечает одним из 30 классов. Пример из отчёта: огурец распознан как томат с уверенностью 78 %. Фильтр культуры только прячет чужие классы.
11. **TTS ненадёжен.** Озвучка работает, только если в системе есть офлайн-голос ru. На Note 7 зафиксирован `onDone` при нулевой громкости. Встроенного движка нет.
12. **Потеря данных.** `allowBackup=false`, экспорт без фото, импорта нет. Удалил приложение — потерял журнал.
13. **Зависимости.** Половина задана строками в обход version catalog. `core-ktx 1.10.1`, `lifecycle 2.6.1`, `activity-compose 1.8.0` старые на фоне Compose BOM 2026.02 и compileSdk 37. Нет coroutines и Flow: используются `Executors` + `Handler`. В release выключен R8, нет signing config, `versionName = "0.16-model-lab"`.
14. **Сборка не воспроизводима из Git.** `*.onnx` и `assets/voice/ru/` в `.gitignore`. При чистом клоне APK соберётся, но без моделей и голоса, а скрипта загрузки нет.

### 4.2 ML и данные

1. Слабые приоритетные классы: здоровый картофель AP50–95 ≈ 0,015 (1 снимок в val), клещ 0, болезни огурца отсутствуют, томатные болезни 0,13–0,55.
2. Test пересекается с train версиями одних и тех же фото, поэтому все прежние метрики условные.
3. Домены смешаны: PlantDoc (поле, интернет-фото), PlantVillage (лист на однотонном фоне), OLID (лист на чёрном сатине). Модель может учиться отличать фон, а не болезнь.

## 6. Новая концепция продукта

### 6.1 Позиционирование

**AgroVoice** — офлайн-ассистент агронома для осмотра картофеля, томата и огурца в поле и теплице. Он фотографирует лист по голосу, выдаёт **предварительную** оценку состояния, по явному запросу подсказывает меры защиты по белорусскому Госреестру, ведёт журнал осмотров с координатами и синхронизирует его с сервером хозяйства, когда появляется сеть.

Это система поддержки решений (СППР), а не система назначения обработок. Любой ответ модели помечен как предварительный, а рекомендации даются только со ссылкой на источник.

### 6.2 Границы MVP для защиты

**Входит:**
- 3 культуры: картофель, томат, огурец. Остальные классы PlantDoc остаются в lab-сборке как история.
- Около 12–16 классов «культура + состояние» по фактически доступным данным (кандидаты ниже).
- Класс или порог «неизвестно / не лист / сфотографируйте ближе».
- Голос: кнопка гарнитуры или фраза-активатор → команда со слотами → озвученный ответ.
- Справочник СЗР по этим классам.
- Журнал в Room, GPS, участки и ряды, фото.
- Сервер: синхронизация, веб-панель, отчёты.

**Не входит** (честно указывается в записке как развитие): процент поражения (только если останется время, см. этап 6), внешние камеры, ESP32, интеграция с 1С.

Кандидаты классов для обсуждения с руководителем (финальный список — по реальным данным после фиксации, этап 2):
картофель — здоровый, фитофтороз, альтернариоз; томат — здоровый, фитофтороз, альтернариоз, септориоз, бактериальная пятнистость, кладоспориоз (бурая пятнистость), мозаика, повреждение клещом / минёром; огурец — здоровый, мучнистая роса, ложная мучнистая роса (пероноспороз), антракноз.

### 6.3 Роли и сценарии

| Роль | Сценарии |
|---|---|
| Агроном (телефон) | Выбрать участок → «Агроном, сфотографируй» → «Обнаружен фитофтороз томата, предварительно, уверенность высокая» → «Чем лечить?» → озвучка 1–3 препаратов с нормой и сроком ожидания + «сверьтесь с этикеткой» → «Сохрани, ряд четырнадцать, заметка: …» → запись в журнале с GPS |
| Агроном (без голоса) | Те же действия кнопками, крупными для работы в перчатках |
| Руководитель / главный агроном (веб) | Карта и таблица осмотров, фильтр по культуре, болезни, участку и дате, просмотр фото, отметка «подтверждено специалистом», экспорт XLSX/PDF |
| Администратор (веб) | Пользователи, участки, публикация новой версии справочника и модели |

### 6.4 Голосовой диалог (конечный автомат)

```
IDLE ──(кнопка гарнитуры / «Агроном»)──▶ LISTEN_COMMAND (до 6 с)
LISTEN_COMMAND ──«сфотографируй»──▶ CAPTURE ─▶ ANALYZE ─▶ SPEAK_RESULT ─▶ AWAIT_FOLLOWUP (15 с)
AWAIT_FOLLOWUP ──«чем лечить»──▶ SPEAK_TREATMENT ─▶ AWAIT_FOLLOWUP
AWAIT_FOLLOWUP ──«сохрани [ряд N] [заметка …]»──▶ SAVE ─▶ «Сохранено» ─▶ IDLE
AWAIT_FOLLOWUP ──«повтори» / «ещё раз» / «отмена»──▶ …
любое состояние ──«стоп»──▶ IDLE
```

Слоты: номер ряда / участка, культура («это огурец» — принудительная культура для классификации), оценка («верно» / «неверно»), текст заметки.

## 8. Функциональная спецификация итоговой версии

### 8.1 Экраны приложения (сборка `field`)

1. **Главный / Осмотр** — текущий участок и ряд, большая кнопка «Снять», индикатор голоса, последний результат.
2. **Камера** — превью, фокус по тапу, подсказка «ближе / светлее» (простая проверка резкости и экспозиции), спуск голосом, кнопкой гарнитуры или на экране.
3. **Результат** — фото с рамками, по каждому листу «культура — состояние — уровень уверенности (высокий / средний / низкий)», плашка «предварительно». Кнопки «Чем лечить», «Сохранить», «Неверно».
4. **Справочник** — болезнь: симптомы, фото-примеры, профилактика, препараты (д. в., норма, кратность, срок ожидания, класс опасности), источник и год.
5. **Журнал** — список и карта, фильтры, карточка осмотра, отметки «подтверждено» / «ошибка модели».
6. **Участки** — список полей и теплиц, текущий участок; синхронизируется с сервером.
7. **Настройки** — голос (гарнитура / фраза / выкл), озвучка, сервер и логин, статус синхронизации, «О модели» (версия, классы, ограничения).

Сборка `lab` дополнительно содержит текущие экраны: 9 моделей, порог, сравнение, бенчмарк.

```
           expert_status[none|confirmed|rejected], model_version, sync_state, updated_at)
photo(id UUID, inspection_id, local_path, sha256, width, height, uploaded)
detection(id, photo_id, class_code, confidence, x1,y1,x2,y2)
disease(code, crop, name_ru, latin, symptoms, prevention, kb_version)
treatment(id, disease_code, product, active_substance, rate, max_treatments, waiting_days, hazard_class, source, year)
kb_version(version, published_at, source_note)
```

### 8.3 API сервера (v1)

| Метод | Назначение |
|---|---|
| `POST /auth/login` | JWT |

| Требование | Цель | Как проверяем |

| Качество модели | mAP50, per-class P/R, матрица ошибок на **собственном** test | скрипт оценки |
