## Что делаем

Android-приложение для осмотра растений: фотография → предположение о культуре и состоянии листа → справочная информация → запись в журнал. Основные функции должны работать без интернета. Сначала управление фиксированными голосовыми командами, позднее — понимание естественных формулировок.

Промежуточный показ: среда, 7 октября 2026 года. Достаточно показать реальный прогресс; APK желателен. Основная сдача ожидается в мае 2027 года. Ближайший приоритет — исправить данные и обучить пригодную модель, затем подключить её к приложению.

Согласованные условия:

- Сохраняем все 29 классов PlantDoc. Полноценное покрытие культур Беларуси потребует дополнительных данных.
- Приоритет первой полевой версии: картофель, томаты и огурцы. Огурцы отсутствуют в PlantDoc; класс Squash Powdery mildew leaf не заменяет огурец.
- Можно добавлять полезные датасеты без отдельного согласования. Для каждого записывать источник, лицензию, классы, число изображений, обработку и причину добавления.
- Рекомендации прежде всего для Беларуси; материалы для РФ должны иметь явную отметку страны. Источники и проверку содержания определяет Борис.
- Встроенная камера телефона — первый вариант. Внешнюю камеру можно добавить позже.
- Основные устройства для проверки: Samsung A56 8/128 и Redmi Note 7 6/64. Желательна совместимость с Redmi 9T. Скорость измеряем на устройствах.
- Размер приложения допустимо увеличить ради автономности; скорость и расход памяти всё равно проверяем.
- Сервер обязателен в итоговой версии для синхронизации/резервных копий и дальнейшей совместной работы. Его реализацию откладываем; автономность основных функций сохраняется.

PlantDoc размечает целый лист и его состояние. Модель не измеряет процент поражённой ткани. Чтобы выдавать такой процент, нужна отдельная разметка пятен/масок и проверка способа измерения. Также confidence модели — оценка уверенности, а не доля повреждения листа. [Описание исходного датасета](https://arxiv.org/html/1911.10317).

## Как пользоваться обучением

Открыть PowerShell в F:\agrovoice-ai. Скрипты запускают процесс в фоне и записывают пути логов; закрытие чата не останавливает его. Выключение компьютера останавливает обучение, но сохранённые эпохи можно продолжить.

```powershell
# Состояние последнего запуска
.\ml-pipeline\Get-TrainingStatus.ps1

# Резервный запуск YOLO26n на CPU
.\ml-pipeline\Start-Training.ps1 -Backend cpu -Epochs 60 -ImageSize 416 -Batch 16

# На AMD через подготовленный WSL
.\ml-pipeline\Start-Training.ps1 -Backend wsl -Epochs 60 -ImageSize 416 -Batch 16

# Мягкая остановка: закончить эпоху и сохранить модель
.\ml-pipeline\Stop-Training.ps1

# Продолжить в той же среде; подставить путь своего запуска
.\ml-pipeline\Start-Training.ps1 -Backend cpu -Resume 'F:\agrovoice-ai\runs\detect\ИМЯ_ЗАПУСКА\weights\last_complete.pt'
```

Не запускать второй эксперимент, пока первый работает: launcher проверяет PID. После Stop дождаться running=false в статусе. При возобновлении сохраняются параметры исходного эксперимента, включая общее число эпох; -Epochs не продлевает законченный эксперимент. После перезагрузки процесс сам не запускается. Восстанавливаемся из last_complete.pt в той же среде и с тем же датасетом. Перенос незаконченного эксперимента между Windows и WSL пока не проверен.

Основной запуск по умолчанию: YOLO26n, изображения 416×416, batch 16, AdamW, до 60 эпох, ранняя остановка после 20 эпох без улучшения. Для другой архитектуры использовать -Model и -Name. AMP по умолчанию выключен после выявленного расхождения на AMD. Это параметры текущего прототипа, не доказательство оптимального качества. Старые веса не продолжаем на изменённой выборке: начинаем отдельный эксперимент от исходных весов COCO.

После каждой завершённой эпохи появляются weights/last_complete.pt и progress.json. Копия контрольной точки заменяется через временный файл; это уменьшает риск потери ранее сохранённой эпохи, но не гарантирует сохранность при аппаратном сбое. Best.pt — лучшая модель для использования. Results.csv — метрики по эпохам. Run_manifest.json — среда, параметры, отпечаток данных и состояние. ONNX экспортируется после обучения, если не задан -NoExport. Ошибка экспорта не означает, что сами веса пропали.

В train_clean.py тестовая выборка используется при явном --test или -Test. Отдельный evaluate_clean.py по умолчанию проверяет val; для итоговой проверки выбранной модели на test нужно передать --test. Повторно использует сохранённый test_metrics.json. Для сравнения вариантов использовать val, не подбирать гиперпараметры по результатам test. Каталоги данных, WSL, окружения, логи и тяжёлые веса исключены из Git; исходники и небольшой отчёт данных сохраняем в репозитории.

Проверка подготовки данных:

```powershell
.\ml-pipeline\venv\Scripts\python.exe -X utf8 -m unittest discover -s ml-pipeline\tests -v
.\ml-pipeline\venv\Scripts\python.exe -X utf8 ml-pipeline\train_clean.py --check
```


YOLO26m разрешена новым предложением Бориса: [отдельный протокол](docs/experiments/yolo26m_v1/PROTOCOL.md). Официальные веса скачаны, GPU M ещё не запускался. Сначала закончить10S/выбор; потом M-пилот на том же рецепте и телефон, затем9 оставшихся при успешной проверке. Не добавлять M в замороженную очередьS и не запускать два GPU-worker.
