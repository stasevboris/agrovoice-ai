# Серия по десять обучений YOLO11n и YOLO26n

Дата: 3 октября 2026. Это 20 новых обучений; прежние два запуска на clean v1 в эту серию не входят.

Статус и результаты очереди: [study10_v2/REPORT.md](study10_v2/REPORT.md), [status.json](study10_v2/status.json), [plan.json](study10_v2/plan.json). Таблица обновляется после завершения обучения и обеих проверок очередной модели. До этого она показывает ноль готовых результатов, даже если первый запуск уже обучается.

## Данные

Заморожена dataset_clean_v2, отпечаток `7306a09a94cfccb1854707d86e45de654a403145dffc59d92d38cbc5b694d5bc`. 2609 train, 349 основная val, 236 test, 160 отдельная val_aux. Первые 29 ID сохранены, ID 29 — Cucumber leaf (condition unknown). [Источники и обработка](../data/dataset_clean_v2.md).

Основная val/test PlantDoc не изменены ни по файлам, ни по рамкам. Основная оценка содержит 29 представленных классов, огурцов там нет. Лабораторные снимки и огурцы проверяются отдельно; их более простые фоны не повышают основную сводную метрику.

## Повторы

- Десять seed: 20261003–20261012, одинаковые пары для двух архитектур. Порядок YOLO11/26 чередуется по seed.
- Каждый запуск начинается заново с исходных весов COCO соответствующей nano-модели. Один процесс обучения на GPU за раз.
- По 60 эпох, 416×416, batch 16, AdamW, lr0 0.001, cos_lr, FP32, одинаковые штатные аугментации. Patience 60 обеспечивает полный бюджет 60 эпох; прежние одиночные эксперименты использовали patience 20 и тоже дошли до 60.
- WSL AgroVoice-ML, PyTorch ROCm, RX 9060 XT. Версии среды, SHA-256 исходных весов и кода записаны в plan.json.
- Перед запуском проверяются отпечаток данных, контрольные суммы изображений/разметки и порядок классов. На каждом следующем шаге проверяются неизменность манифеста и исходных весов.
- После каждого обучения: основная val, отдельная val_aux, проверка экспорта ONNX относительно PyTorch. TEST не используется в подборе архитектуры.

Сводка: среднее, выборочное стандартное отклонение, минимум/максимум по десяти seed, парная разница YOLO26−YOLO11 и показатели классов каждого запуска. Это вариативность обучения на одном разбиении данных, а не десять независимых полевых исследований.

По завершении 20 запусков выбирается архитектура с большим средним основным val mAP50–95, затем её запуск с наибольшим val mAP50–95. Его test проверяется один раз и создаётся пакет модели. Выбор лучшего seed делает val оптимистичной; этот результат нельзя выдавать за среднее качество архитектуры. Первоначальные показатели test clean v1 уже были просмотрены, поэтому для финальной дипломной оценки всё равно нужна новая внешняя полевая выборка.

## Запуск, остановка и восстановление

```powershell
# Новая очередь (уже запущена 3 октября)
.\ml-pipeline\Start-Study.ps1

# Статус текущего обучения и общая очередь
.\ml-pipeline\Get-TrainingStatus.ps1
Get-Content .\docs\experiments\study10_v2\status.json

# Завершить текущую эпоху, сохранить checkpoint и остановить всю очередь
.\ml-pipeline\Stop-Training.ps1

# После остановки/выключения компьютера: продолжить незавершённый seed,
# пропустить уже проверенные модели и затем выполнить оставшиеся
.\ml-pipeline\Start-Study.ps1 -Resume
```

Start-Study запускает скрытый процесс WSL. Отдельные логи обучения и проверок находятся в `ml-pipeline/logs/study10_v2`. При ошибке очередь прекращается; причина попадает в status.json/логи. Автоматического восстановления после выключения ПК нет: нужно запустить команду Resume. Не следует запускать самостоятельное обучение одновременно с очередью; launcher проверяет активный процесс.

В первом предварительном запуске очередь остановилась до обучения: бинарное хеширование JSON учитывало CRLF Windows, а подготовка рассчитывала отпечаток текста с LF. Проверка исправлена на канонический текст, контрольные суммы реальных изображений/меток по-прежнему бинарные. Неудавшийся предварительный протокол сохранён как plan_preflight_failed_01.json; ни одного обученного результата он не создал.

## Повторы на телефоне

Независимая от обучения процедура: `repeat_phone_benchmark.py` выполняет по десять свежих процессов каждой архитектуры на Redmi Note 7, 10 прогревов + 40 измерений в каждой серии, чередующийся порядок, пауза 10 секунд. Все пять входов и обе модели проверяются по SHA-256, первый сырой выход каждой серии сравнивается с настольным ONNX, записываются условия батареи/температуры до и после. Свежесть JSON определяется уникальным run_id.

Используются **прежние веса clean v1**. Это проверка воспроизводимости старого замера телефона, а не скорость ещё не обученной модели clean v2. Сводка считает среднее/SD медиан отдельных серий, не выдаёт 800 измерений за 800 независимых устройств. Камера, декодирование/масштабирование фото и отрисовка исключены. Итоги: [redmi_note_7_10series/REPORT.md](redmi_note_7_10series/REPORT.md).
