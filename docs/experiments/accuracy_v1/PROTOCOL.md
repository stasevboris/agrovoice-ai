Разрешена Борисом 4 октября 2026: попробовать все пять предложенных направлений и добавить готовые варианты в автономный APK. Это отдельная серия; clean v2 и три защищённых скрипта study10_v2 сохраняются.

## Направления

1. YOLO26n + классификаторы MobileNetV3-Large / EfficientNet-B0 на вырезках листьев.
2. Небольшой DETR: DEIMv2-N, резерв D-FINE-N при проблеме совместимости.
3. YOLO26s как более крупный одноступенчатый детектор.
4. Небольшая сегментационная сеть для маски **целого листа** + классификатор. Поражённые участки/процент болезни не заявляются без отдельных масок.
5. Более крупный классификатор-учитель + компактный ученик с дистилляцией.

## Начальные данные и оценка

Первый контролируемый этап использует ту же clean v2; производные crop/COCO/masks имеют отдельный manifest. Сначала разделение исходных кадров/групп, затем нарезка. Вырезки из большого фото, запас 10% с каждой стороны, максимум 512 пикселей. Модель получает 224×224 с пропорциональным вписыванием. Ни один новый кандидат-архив не считается источником старой серии.

Все 30 ID сохраняются. Огурец пока «состояние неизвестно». Истинных диагнозов огуречных болезней и независимого test здорового картофеля/клеща в текущем наборе нет. Высокая accuracy готовых crop не заменяет оценку всех найденных/пропущенных листьев.

Предварительная проверка: совместимость AMD/ROCm, оптимизатор, экспорт ONNX FP32, численный паритет, Android CPU. После технической проверки — десять seed 20261003–20261012 на каждый итоговый вариант. Разведочный seed не выдаётся за итог десяти. Рецепт другого семейства записывается отдельно; сравнение учитывать по бюджету/полученному качеству, а не насильно по одному неподходящему оптимизатору.

Выбор checkpoint и варианта — по основной val. val_aux/mask IoU отдельно. Итоговый test выбранных вариантов — после выбора, не после каждой настройки. Старый test уже просмотрен в истории; для финального дипломного вывода необходим новый внешний полевой контроль.

Классификация: macro-F1, balanced accuracy, precision/recall по каждому классу, confusion matrix и число примеров. Для цепочки: class-aware AP и пропуски, ложные рамки, качество диагноза на предсказанной вырезке. Для масок лабораторный IoU не объявлять полевым качеством. Для телефона — весь путь фото, 1/несколько листьев, память, повторные измерения, точные SHA графов.

## Правила исполнения

Фактическая общая очередь — architecture_queue.py, 80 заданий: 8 компонентов ×10 seed. Первый MobileNet завершён прежним компонентным worker; второй мягко остановлен после8 эпох, checkpoint сохранён. Новый dispatcher сначала проходит все компоненты seed20261003, затем20261004 и далее. Classification_plan.json сохраняет исходные данные и рецепты; architecture_plan.json добавляет два детектора и порядок. Их численные параметры не менялись.

Основной статус — architecture_status.json. Status.json описывает остановленную первоначальную компонентную очередь и не означает, что GPU сейчас свободна. Проверять общий active_training.json и Get-AccuracyStatus.ps1. При продолжении: Start-AccuracyStudy.ps1 -AllArchitectures, только после фактического выхода записанного процесса.

Все варианты сравнивать общим evaluate_accuracy_pipeline.py: CPU ONNX, class-aware AP50–95, fixed-threshold диагноз и пропуски. Для ten-seed режима --seeds20261003...20261012 (отдельные аргументы); для цепочек детектор/классификатор берутся с одинаковым seed. Базовые20 уже повторно проверены. Новые pretrained/random-head CPU-пробы проверяют совместимость, не точность и не готовность к APK. APK пока использует предварительный MobileNet03 с выбранным базовым детектором12; pairing явно сохранён.

Для дистилляции дополнительно оценивается реальный учитель на полном фото через evaluate_accuracy_teacher.py --seeds20261003...20261012: он вызывает ту же CPU evaluate(), использует детектор26n с тем же seed и сохраняет весь стандартный отчёт. Это вспомогательный контроль предела качества учителя, не дополнительное GPU-обучение или отдельный APK-режим. code_sha256 относится к общему evaluator, launcher_code_sha256 — к вспомогательной обёртке. Неготовые учителя явно пропускаются; в статистике сохраняется фактическое n. Исходная очередь80 заданий и финальные шесть новых диагнозных режимов не изменены.

Финальный выбор внутри нового варианта делать по общей end-to-end val, а не только по метрике GT-crop. Package_accuracy_models.py при10 завершённых обучениях и10 общих paired-оценках выбирает seed по AP50–95 полной цепочки и включает соответствующий seed детектора. После упаковки заново проверять графы и смартфон. Пока полного набора нет, выбор предварительный по метрике компонента; metadata сохраняет provisional и число paired-оценок. Test остаётся вне подбора.

Один GPU-worker; очередные задания последовательно, контрольные точки после каждой эпохи, resume без изменения данных/плана. Скачивание/CPU-подготовка и Android-сборка могут идти во время обучения, но без второго GPU-обучения. Не заменять ROCm/PyTorch или драйвер автоматически ради чужого requirements.txt.

В APK включать только реальные обученные, экспортированные и проверенные графы. В manifest хранить семейство, формы, preprocess/postprocess, seed, источник и SHA; в JSON — происхождение всех стадий. Незавершённые направления не маскировать готовой кнопкой.

### Уточнение проверки экспорта DEIM, 4 октября

Первый DEIM завершил60 эпох, но прежний экспортный guard остановил очередь: в трёх raw TopK выходах были различия слабых рамок до0,28772 пикселя. Диагностика сравнила PyTorch с/без MKLDNN и ONNX с тремя уровнями оптимизации, затем все349 val-фото исходного checkpoint, deployed PyTorch и ONNX. На всей val исходный AP50–95=0,30093070165, deployed=0,30093071215, ONNX=0,30093014141; AP50 также изменился менее чем на0,000001. Строгий raw guard не прошёл136 фото; у фоновых TopK кандидатов были четыре изменения class ID и максимальное ошибочное сопоставление322,6 пикселя. Эти сырые выходы не объявляются идентичными. Все кандидаты с score≥0,1 в полном сопоставлении прошли прежние atol0,003/rtol0,0001.

Проверка обученных DEIM теперь для каждого seed проходит всю val: отдельно сохраняются raw различия, взаимно однозначно проверяется полный набор видимых кандидатов score≥0,1 (минимум slider APK) с точным class ID и прежними численными допусками; AP50/AP50–95 сравниваются для всех кандидатов score≥0,001 и maxDets300, максимальная допустимая разница0,0001. Проверка исходной и deployed моделей также обязательна. Ни граф, ни порог общего AP evaluator, ни training recipe не изменены. Test не используется. Проверка телефона для DEIM также охватывает все потенциально видимые кандидаты; сырые300 строк остаются в бинарных следах. Остальные семейства сохраняют строгий raw паритет. export_validation.json хранит каждый снимок, AP, policy, SHA графа и кода проверки. Первоначальный SHA обучавшего скрипта сохраняется в manifest; экспортный SHA записывается отдельно. --export-only завершает уже обученный checkpoint без GPU-обучения.
