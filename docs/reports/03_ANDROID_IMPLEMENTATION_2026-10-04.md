# Автономный Android-прототип: реализация и испытания

Срез на 4 октября 2026. Готовый файл: [AgroVoice-field-demo-0.2.apk](../../artifacts/apk/AgroVoice-field-demo-0.2.apk). APK установлен на подключённый Redmi Note 7. Здесь подробно записаны устройство программы, фактические проверки, обнаруженные ошибки и ограничения. Краткая пользовательская инструкция — [FIELD_DEMO](../android/FIELD_DEMO_2026-10-03.md).

## 1. Назначение версии 0.2

Приложение позволяет проверить нейронную сеть на собственной фотографии: сделать снимок штатной камерой или импортировать готовый, увидеть рамки листьев, названия предполагаемых состояний и confidence. Есть переключатель YOLO11n/YOLO26n, повторная обработка, фильтр культуры и регулировка порога. Каждая успешная обработка оставляет JSON с происхождением результата.

Это локальная debug-сборка для испытаний. Она не опубликована, не является готовым агрономическим консультантом и не содержит голоса/сервера/лечебных рекомендаций. Приложение использует выбранный файл фотографии; графы исполняются на телефоне, сетевых разрешений нет.

## 3. Пользовательский сценарий

1. Открыть AgroVoice AI. На подключённом Note 7 приложение уже установлено.
2. Нажать «Сделать фото» и подтвердить кадр штатной камерой либо нажать «Из галереи» и выбрать изображение. Отмена камеры возвращает в приложение с сообщением.
3. Подождать локальную обработку. На экране появятся рамки, номера и карточки с русскими подписями и confidence.
4. Переключить модель, сохраняя тот же снимок. Это позволяет увидеть разные предположения, но не устанавливает истинный диагноз.
5. Выбрать культуру при необходимости. Это фильтр уже полученных классов. Если сеть назвала огурец виноградом, фильтр огурца уберёт виноград, но не переобучит сеть и не превратит ответ в правильный.
6. Изменить порог: по умолчанию 0,25, доступный диапазон 0,10…0,80. Меньший порог показывает больше кандидатов и ложных рамок, больший может скрыть реальные листья.

Сообщение «нет обнаружений» означает, что при текущей модели/пороге/фильтре нет подходящих рамок. Оно не означает «растение здорово». Подпись без заболевания означает класс источника без указанной болезни; уверенное распознавание такого класса не гарантирует отсутствия поражения.

## 4. Обработка изображения по шагам

### 4.1. Получение файла

Камера вызывается через Activity Result TakePicture. Для нового кадра создаётся личный файл `camera_<UUID>.jpg`; FileProvider предоставляет приложению камеры временный доступ к этому конкретному пути. Сам AgroVoice не запрашивает CAMERA, поскольку не открывает собственный видеопоток.

Галерея открывается системным Photo Picker. Доступ даётся к выбранному URI. Содержимое копируется в личную папку приложения с уникальным именем; используется копия, а не предположение о постоянном доступе к исходному URI. При чтении ограничение 64 MiB; при ошибке неполная копия удаляется. Расширение выбирается по MIME (JPEG/PNG/WebP/HEIC/HEIF), но успешность декодирования последних форматов зависит от платформенного кодека и не была отдельным тестом.

### 4.2. Декодирование и EXIF

Сначала BitmapFactory читает размеры без полной загрузки. Подбирается степенной inSampleSize так, чтобы большая сторона декодированного изображения не превышала 2048. Для нечётных исходных размеров проверен реальный результат. Используются ARGB_8888 и sRGB. Если файл не является читаемым изображением, показывается понятная ошибка.

ExifInterface применяет все восемь ориентаций: нормальная, горизонтальное/вертикальное отражение, 180°, 90°, 270° и два сочетания отражения с поворотом. При замене bitmap прежняя копия освобождается. Рамки впоследствии выражаются в координатах **ориентированного декодированного фото**, а не исходного полноразмерного JPEG до поворота.

### 4.3. Подготовка входа сети

Изображение пропорционально вписывается в 416×416. Остальные области заполнены цветом 114 (letterbox), геометрия листа не растягивается. Запоминаются масштаб и поля для обратного преобразования рамок. Каналы идут RGB, значения делятся на 255, данные расположены NCHW в float32.

### 4.4. Загрузка и исполнение

Ассеты модели сначала копируются в `filesDir/models/<id>_<sha12>.onnx`; SHA-256 проверяется. ONNX Runtime открывает одну активную сессию. При переключении прежняя сессия закрывается. Таким образом, хранение двух графов в APK не означает две одновременно загруженные модели в RAM.

Обработка вынесена в один Executor, чтобы не блокировать UI и не запускать две работы одновременно. CPU-конфигурация: четыре intra-op потока, один inter-op. GPU/NPU и ускорители NNAPI не включались. Флаг KEEP_SCREEN_ON действует пока экран приложения видим.

### 4.5. Обработка кандидатов

Из выхода `[1,34,3549]` читаются геометрия и 30 оценок классов; для кандидата выбирается максимальный класс. Проверяется конечность чисел, применяется порог. Дубли удаляются **отдельно для каждого класса** с NMS IoU=0,7, максимум 300 детекций и предварительный предел 30 000 кандидатов.

NMS выполняется в сетевых координатах до обрезания рамок. Затем вычитаются поля letterbox, применяется обратный масштаб и координаты ограничиваются изображением. Рамки разных классов могут перекрываться: это следствие class-aware NMS и неоднозначных выходов, а не обязательно два разных физических листа.

### 4.6. Отрисовка и сохранение

Фото показывается через ContentScale.Fit в области высотой 340dp. Координаты рамок учитывают текущий размер области, масштаб и экранные поля. В каждой рамке виден номер; карточка результата содержит соответствующую подпись. Поворот экрана не должен менять файл фотографии или выбор модели.

После успешной обработки сохраняются результаты и последний путь к фото. Настройки модели, культуры, порога и ожидающий camera-path хранятся в SharedPreferences; состояние обработки управляется ViewModel. Есть проверка восстановления после перезапуска и после поворота. Восстановление процесса в любой возможный момент работы камеры не исследовано исчерпывающе.

## 6. Разрешения и данные

В окончательном merged manifest нет INTERNET и ACCESS_NETWORK_STATE. Они удалены в том числе из зависимости ONNX Runtime. Её автоматический `ai.onnxruntime.TelemetryInitializer` тоже исключён. Микрофон и широкий доступ ко всей галерее не запрашиваются. Утверждение об автономности основывается на локальном вызове модели и проверенном manifest; отдельная длительная сетевая трассировка не проводилась.

Личные файлы на испытанном телефоне:

```text
/sdcard/Android/data/com.agronomy.phytomonitor/files/photos/
/sdcard/Android/data/com.agronomy.phytomonitor/files/results/
```

При недоступности external-files код использует внутреннюю filesDir. Общие демонстрационные фотографии лежат отдельно:

```text
/sdcard/Pictures/AgroVoice_Field_Test/
```

Удаление приложения удаляет его личные фото/JSON; общие примеры остаются. AutoBackup отключён. Прототип не реализует экспорт/импорт настоящего журнала, резервную копию, синхронизацию или автоматическую очистку старых файлов; долгое ручное использование может накопить снимки и результаты. Личные пути Android/data на новых прошивках удобнее читать через ADB, чем обычным файловым менеджером.

### Поля JSON результата

| Поле | Смысл |
|---|---|
| created_epoch_ms | Время сохранения результата |
| photo, photo_sha256 | Путь к использованной копии и её SHA-256 |
| decoded_width / decoded_height | Размер после декодирования и EXIF |
| coordinate_space | Явное описание пространства координат рамок |
| model / model_sha256 | ID графа и контрольная сумма фактически выбранного файла |
| dataset / seed / provisional | clean v2, seed 20261003, предварительная пара |
| crop_filter / confidence_threshold | Условия отбора отображаемых результатов |
| inference_ms / pipeline_ms | Создание ONNX-тензора + граф; загрузка модели при необходимости + подготовка входа + граф + NMS; не время всей работы пользователя |
| detections | ID, исходный класс, русская подпись, confidence, xyxy в пикселях |
| device / scope | Производитель/модель телефона и ограничения интерпретации |

`inference_ms` начинается перед созданием OnnxTensor и заканчивается после session.run; чтение выходного массива/NMS туда не входят. `pipeline_ms` начинается внутри FieldDetector.detect перед load(model) и заканчивается после NMS. Декодирование исходного файла, отрисовка, запись JSON и время выбора/съёмки находятся за пределами обоих таймеров. Холодный первый detect может включать создание сессии и потому заметно отличаться от тёплого.

Сейчас seed=20261003 и provisional=True записаны в PhotoFiles как параметры текущего APK. При интеграции выбранных весов надо перенести происхождение в данные модели и сохранять актуальные значения, иначе новая нейронка будет оставлять ложный seed в JSON. Одной подмены ONNX-файла недостаточно.

На отдельно выбранном в UI `10_cucumber_powdery_mildew.jpg` обе сети выдавали класс **Squash Powdery mildew**, а не обученный диагноз огурца. Интерфейс сохраняет исходный смысл Squash; фильтр огурца убирает эту ошибочную культуру.

Нельзя объявлять модель надёжной, потому что она быстро нарисовала уверенную рамку. Эти ошибки уже существуют в проверенных примерах и являются основанием дополнять данные и проводить внешнее испытание. Набор не имеет полноценной независимой разметки, поэтому метрика точности по десяти фото не считается.

## 9. Проверка вычислений Android и компьютера

Для одного и того же реально подготовленного на Android тензора первой фотографии сохранены бинарные входы/выходы. Настольный CPU ONNX Runtime 1.26.0 исполнил тот же граф. Допуски rtol=0,0001, atol=0,002. Для проверки NMS использован тот же Android-выход и upstream Ultralytics, затем преобразование в координаты снимка.

| Модель | Desktop ORT | Max abs выхода | Mean abs выхода | Совпавших рамок | Max ошибка рамки, px |
| --- | --- | --- | --- | --- | --- |
| yolo11n | 1.26.0 | 0.001159668 | 0.000003271 | 2 | 0.00004102 |
| yolo26n | 1.26.0 | 0.001281738 | 0.000002663 | 3 | 0.00005762 |

На этом примере совпали две рамки YOLO11n и три YOLO26n; ошибка координат <0,00006 пикселя. Это сильное подтверждение правильного чтения тензора, NMS и геометрии для проверенного сценария. Оно не проверяет все возможные снимки, шесть разных изображений или агрономическую истинность классов.

Отдельно готовый выбранный seed 20261012 прошёл ONNX/PyTorch на компьютере, но это другая проверка другого файла. После замены весов телефонная сверка должна повториться.

## 10. Скорость, память и ограничения измерений

Ранее проведены десять серий каждой архитектуры на **clean v1**, по 10 прогревов/40 измерений, свежий процесс и чередование моделей. Среднее десяти медиан графа+обработки: YOLO11n 122,39±0,60 мс, YOLO26n 107,89±0,65 мс. Камера, декодирование, масштабирование и отрисовка исключены. [Отчёт и исходные серии](../experiments/redmi_note_7_10series/REPORT.md).

Текущие шесть JSON clean v2 демонстрируют исполнение обеих моделей на телефоне, но не повторяют тот протокол. Нельзя обещать, что пользователь всегда получит полный результат за 108 мс: импорт, чтение большой фотографии, создание модели и UI добавляют время.

В одном наблюдении приложения PSS составлял 140 770 KiB, RSS 204 004 KiB. Это единичный снимок до окончательной переустановки, а не измеренный пик/минимум/требование RAM. Долгий нагрев, расход батареи, нагрузка при многочасовых осмотрах и устойчивость после десятков переключений не измерялись. Размер 86 MiB APK включает debug-обвязку, нативные библиотеки двух ABI и два графа; подробный вклад каждой зависимости пока не профилирован.

## 12. Как воспроизвести техническую проверку

Сборка из существующих файлов:

```powershell
Set-Location F:\agrovoice-ai\android-app
.\gradlew.bat :app:assembleDebug --max-workers=2 --console=plain
```

Проверка подключённого устройства и установка текущего артефакта без очистки данных:

```powershell
& 'C:\Users\Boris\AppData\Local\Android\Sdk\platform-tools\adb.exe' devices -l
& 'C:\Users\Boris\AppData\Local\Android\Sdk\platform-tools\adb.exe' -s b861c4e0 install -r 'F:\agrovoice-ai\artifacts\apk\AgroVoice-field-demo-0.2.apk'
```

Это команды для повторения при необходимости, а не действия, выполненные при написании данного отчёта. При другом устройстве заменить serial на фактически показанный devices. Текущий опубликованный локальный артефакт имеет указанный SHA; новая сборка может иметь иной SHA и требует собственной записи.

Сценарии проекта:

| Сценарий | Назначение и оговорка |
|---|---|
| prepare_android_demo_models.py | Подготовка предварительной пары seed 20261003; не пакует финальный seed автоматически |
| fetch_field_demo_photos.py | Загрузка оригиналов и manifest происхождения; соблюдать ответы источника |
| verify_android_demo.py | Сверка сохранённых Android-входов/выходов с компьютером |
| finalize_android_demo_report.py | Аудит APK/ассетов/галереи/проверок и замороженных данных |
| repeat_phone_benchmark.py | Исторический повторный бенчмарк графов; протокол следует адаптировать явно для новых весов |

Бинарные модели, APK, большие исходные фото и сырые тензоры исключены из Git. Сохранённые manifest и SHA объясняют, какие внешние/локальные файлы нужны для воспроизведения; Git checkout сам по себе не гарантирует наличие этих артефактов.

## 13. Что осталось для следующей версии

Сначала внедрить выбранные веса seed 20261012 с актуальным manifest/JSON, собрать новую версию и повторить импорт, переключение, EXIF, паритет и временные замеры. Затем испытать физическую съёмку собственного листа, A56 и по возможности Redmi 9T. Не выдавать отсутствие рамок за здоровье; сохранять неправильные ответы с отметкой пользователя и истинным состоянием, если оно известно.

После полевого испытания добавить постоянный журнал осмотров и экспорт результатов, затем голос и справочник. Работа с болезнями огурцов зависит от будущей разметки и обучения, а не только от новой кнопки интерфейса.
